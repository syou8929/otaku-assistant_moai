# 機能ガイド（新プラグイン説明書）

このドキュメントは、プラグインアーキテクチャ移行後に追加された新機能の**利用者向け説明書**です。
開発者向けの内部仕様は各プラグインの `src/plugins/<名前>/blueprint.md` を参照してください。

> 新しいユニットを実装したら、このガイドに利用者向けの節を追記すること（完了条件の一部）。

---

## 0. はじめに — 機能の有効化（loadout）

新機能はすべて**既定で無効**です。サーバー（フォーク）ごとに `config.json` の `plugins` ブロックで
有効化します。これを「loadout（そのサーバーの装備構成）」と呼びます。

```json
{
  "plugins": {
    "reminder": { "enabled": true },
    "archive-search": { "enabled": true },
    "decision-log": { "enabled": true, "portalChannelId": "チャンネルID" },
    "pin-portal": {
      "enabled": true,
      "portalChannelId": "チャンネルID",
      "sources": ["公開カテゴリID", "公開チャンネルID"]
    }
  }
}
```

有効化・無効化の手順:

1. `config.json` を編集
2. bot を再起動（`systemctl restart otaku-assistant` など）
3. スラッシュコマンドの増減があるときは `npm run register-commands` を実行

## 1. リマインダー（reminder）

Slack の `/remind` に相当する機能です。指定時刻に DM またはチャンネルへ通知します。

### コマンド

| 操作 | 内容 |
|---|---|
| `/remind add time:<いつ> content:<内容>` | リマインダーを作成（既定は自分宛て DM） |
| `/remind add ... channel:#general` | チャンネルへ通知 |
| `/remind add ... user:@相手` | 相手をメンションして通知 |
| `/remind list` | 自分のリマインダー一覧。セレクトメニューから取り消し |
| メッセージを**右クリック →「このメッセージをリマインド」** | そのメッセージへのリンク付きで後から DM 通知（「あとで返信する」に最適） |

### 時間の書き方

| 書き方 | 例 | 意味 |
|---|---|---|
| 相対 | `30分後` `2時間後` `3日後` | 今からの相対時刻 |
| 当日/翌日 | `18:00` `今日 18時30分` `明日 9:00` `明日` | 過ぎていれば翌日に繰り上げ。「明日」だけなら朝9時 |
| 日付指定 | `6/15 09:00` | 過ぎていれば来年 |
| 定期 | `毎日 9:00` `毎週月 10:00` `毎週金曜 19時` `平日 9:30` | 繰り返し通知 |

### 通知が届いたら

通知メッセージのボタンで操作できます（**作成者と通知対象者だけ**が押せます）:

- **⏰ 10分後 / 1時間後 / 明日9時** — スヌーズ（後でもう一度通知）
- **✅ 完了** — 終了としてマーク

定期リマインダーにはボタンが付きません。停止は `/remind list` から取り消してください。

### 補足

- リマインダーは bot を再起動しても消えません（DB に永続化）
- bot が停止していた間に期限が来た one-shot は、再起動後すぐに配達されます
- サーバーで **quiet hours**（静音時間帯）が設定されている場合、深夜の通知は
  静音明け（例: 朝7時）にまとめて届きます

## 2. ピン留めポータル（pin-portal）

各チャンネルで「ピン留め」されたメッセージを、**1つのポータルチャンネルへ自動で集約**します。
誰も新しい操作を覚える必要はありません — 普段どおりピン留めするだけです。
ピンを外せばポータルからも自動で消えます。

### 設定（管理者）

```json
"pin-portal": {
  "enabled": true,
  "portalChannelId": "ポータルにするチャンネルの ID",
  "sources": ["集約してよいカテゴリ/チャンネルの ID", "..."]
}
```

- **`sources` に列挙したチャンネル/カテゴリのピンだけ**が集約されます（安全のための明示 opt-in）。
  私的なチャンネルのピンが公開ポータルへ出る事故を防ぐ仕組みです
- `/pin-sync [channel]`（管理者）— 過去のピンを手動で取り込み（導入時のバックフィル用）

## 3. 情報バリア（timeline-barrier）

**仕事サーバー向けの中核機能。** タイムライン中継 bot は Discord の権限を越えてメッセージを
コピーできる唯一の存在です。この機能は「機密度の高い場所の投稿が、より公開的な場所へ
中継されること」を bot 自身が機械的に拒否します。

### 考え方: Tier（0〜9）

- チャンネルまたはカテゴリに **Tier（機密度）** を割り当てます。**数値が大きいほど機密**
- 中継が許されるのは「**ソースの Tier ≦ 宛先の Tier**」のときだけ
  - 例: 人事カテゴリ（Tier 5）の投稿は、公開タイムライン（Tier 0）には**流れない**
- **deny-by-default**: バリア有効時、Tier 未割当のソースは最機密（9）、未割当の宛先は公開（0）
  として扱われます。つまり**割り当てていないペアは中継されません**。割り当てて初めて流れます

### コマンド（管理者のみ・応答は本人にだけ表示）

| コマンド | 内容 |
|---|---|
| `/timeline-barrier set target:#チャンネルやカテゴリ tier:0〜9` | Tier を割り当て |
| `/timeline-barrier remove target:...` | 割り当てを解除 |
| `/timeline-barrier list` | 割り当て一覧とバリアの状態 |
| `/timeline-barrier test source:... destination:...` | 中継できるか事前確認（dry-run） |

### 有効化（管理者）

```json
"timeline-relay": {
  "enabled": true,
  "barrier": { "enabled": true }
}
```

**推奨導入手順**: ①バリアは無効のまま `/timeline-barrier set` で全カテゴリに Tier を割り当て →
②`/timeline-barrier test` で主要ペアを確認 → ③`barrier.enabled: true` にして再起動。
順番を逆にすると（割当前に有効化）、deny-by-default により全ての中継が止まります。

## 4. 全文検索（archive-search）

bot が保存している全メッセージのアーカイブを横断検索します。
「あの話どこでしたっけ？」を数秒で解決します。

### コマンド

| コマンド | 内容 |
|---|---|
| `/search query:<検索語>` | 全チャンネル横断で検索（新しい順・最大10件） |
| `/search query:<検索語> channel:#チャンネル` | チャンネル限定 |

### 知っておくこと

- 結果は**自分にだけ**表示されます（ephemeral）
- **自分が閲覧できないチャンネルの内容はヒットしません**（権限で自動フィルタ）
- 検索語は**3文字以上**が高速・高精度です。1〜2文字でも検索できますが部分一致の低速モードになります
- 結果には投稿者・チャンネル・日付・本文の冒頭と**元メッセージへのジャンプリンク**が付きます
- 注意: bot のアーカイブには **Discord 上で削除されたメッセージも残っています**。
  運用ポリシーとしてメンバーに周知してください

## 5. 決定事項ログ（decision-log）

「チャットで決まったことが流れて消える」問題への対策です。会話の結論をワンアクションで
記録し、専用チャンネルに掲示します。

### 使い方

| 操作 | 内容 |
|---|---|
| 結論のメッセージを**右クリック →「決定として記録」** | 本文が入力欄に入った状態で確認画面が開く。編集して確定すると**元メッセージへのリンク付き**で記録 |
| `/decide content:<決定の内容>` | その場で直接記録 |
| `/decisions` | 最近の決定一覧（自分にだけ表示） |
| `/decisions query:<検索語>` | 決定の検索 |

### 設定（管理者）

```json
"decision-log": { "enabled": true, "portalChannelId": "決定を掲示するチャンネルID" }
```

- 記録は**削除されません**（取り消しても履歴として残る append-only 方式）
- 記録するのは常に**人間**です。bot が勝手に「これは決定だ」と判断することはありません

## 6. ミューズ・ガチャ（muse-gacha）

クリエイティブ向けのインスピレーション供給装置です。ジャンルごとに登録した YouTube
チャンネル群から **「今日の3本」** を抽選して配信します。3本のうち1本は**別ジャンルからの
「乱入枠」🎲** — 自分では選ばない映像が視野の外を連れてきます。同じ動画は約60日間
再登場しません（既出回避）。

### 使い方

| 操作 | 内容 |
|---|---|
| `/muse pick [genre]` | 今すぐガチャ（ジャンル未指定ならランダム） |
| `/muse status` | プールの蓄積状況 |
| `/muse crawl` | プールを今すぐ巡回取得（管理者） |
| 定期配信 | `deliveryCron` の時刻に `deliveryChannelId` へ自動投稿（例: 平日朝9時） |

### 設定（管理者）

```json
"muse-gacha": {
  "enabled": true,
  "pools": {
    "MV": ["YouTubeチャンネルID", "..."],
    "モーショングラフィックス": ["..."]
  },
  "deliveryChannelId": "配信先チャンネルID",
  "deliveryCron": "0 9 * * 1-5"
}
```

- チャンネル ID は YouTube チャンネルページの URL（`/channel/UC...`）から取得します
- 外部通信は YouTube RSS（読み取り専用・API キー不要）のみ
- プールは毎日自動巡回で蓄積されます。**導入直後はプールが浅い**ので、初回は
  `/muse crawl` を実行し、数日かけて深くなるのを待ってください

## 7. ニュースダイジェスト（news-digest）

ゲーム・映像・音楽・テック・AI など、カテゴリごとに登録したニュースソース
（RSS / Reddit / Hacker News）を自動巡回し、**毎日決まった時間に「1日1枚」のダイジェスト**を
カテゴリ別チャンネルへ配信します。

- **重複排除**: 同じニュースを報じる複数の記事は1つにまとまります
- **Hot スコア 🔥**: 複数のソースが同時に報じている話題ほど上位に表示されます
- 一度配信した記事は再掲されません。垂れ流しの RSS 転送と違い、通知洪水になりません

### 使い方

| 操作 | 内容 |
|---|---|
| 定期配信 | `digestCron` の時刻（例: 平日朝8時）に自動投稿 |
| `/news status` | 蓄積状況の確認 |
| `/news crawl` | 今すぐ巡回（管理者） |
| `/news now` | 今すぐ配信（管理者） |

### 設定（管理者）

```json
"news-digest": {
  "enabled": true,
  "categories": {
    "テック": {
      "channelId": "配信先チャンネルID",
      "feeds": [
        { "name": "Hacker News", "url": "https://news.ycombinator.com/rss" },
        { "name": "Publickey", "url": "https://www.publickey1.jp/atom.xml" }
      ]
    }
  },
  "digestCron": "0 8 * * 1-5"
}
```

- ソースは RSS/Atom フィードならなんでも登録できます（API キー不要）。
  Reddit は `https://www.reddit.com/r/サブレ名/.rss`、Google News のキーワード
  フィードも使えます
- X / Twitter は非対応です（API 有料化のため設計から除外）

## 8. リファレンスボード（ref-board）

クリエイティブ作業の「参考資料」をプロジェクト別に集めるモードボードです。
会話に流れた画像・リンクをその場で保存でき、**画像はサーバーにも保存される**ので
元ツイートが消えても参照できます（💾 マーク付き）。

### 使い方

| 操作 | 内容 |
|---|---|
| メッセージを**右クリック →「ボードに保存」** | 保存先ボードを選んで保存。「＋新規ボードを作る」でその場で作成 |
| `/ref boards` | ボード一覧と件数 |
| `/ref view name:<ボード名>` | ボードの中身（最新20件） |
| 常設カード | `boardChannelId` のチャンネルにボードごとのカードが自動更新で並ぶ |

### 設定（管理者）

```json
"ref-board": { "enabled": true, "boardChannelId": "ボード一覧チャンネルID" }
```

- 画像の保存は 10MB 以下の画像ファイルのみ。保存先はサーバーの `data/ref-media/`
- 参考資料の社内複製はグレー領域です。**社内限定の利用**を前提にしてください

## 9. 管理者向けメモ

### 静音時間帯（quiet hours — 通知統治）

深夜に bot が人を起こさないようにする設定です。`config.json` のトップレベルに:

```json
"notifications": { "quietHours": { "start": "23:00", "end": "07:00" } }
```

- 静音時間帯に重なった **DM/メンション通知（リマインダー等）は静音明けへ自動繰り延べ**されます
- チャンネルへの定期投稿（ニュース・ガチャ）は対象外です — 配信時刻は各 cron で制御してください
- 未設定なら無効（従来どおり全時刻配達）。**ユーザーが明示した時刻も繰り延べ対象**になる点に注意

### 利用テレメトリ（telemetry）

- `/telemetry [days]`（管理者）— 直近のコマンド・ボタン・ジョブの利用回数と、
  **28日間使われていない「休眠プラグイン」**の一覧を表示します
- 記録は**集計カウントのみ**です（誰が使ったか・内容は一切記録しません）
- 「有効にしたが誰も使っていない機能」を見つけて loadout を剪定するための道具です

### バックアップ（backup — 既定で有効）

- 毎日 4:00 に DB のスナップショットを `data/backups/` へ自動取得し、最新14世代を保持します
  （bot は無停止。`plugins.backup.cron` / `keep` で変更可）
- `/backup now` 今すぐ取得 ／ `/backup status` 世代一覧 ／
  `/backup export` 決定事項ログを markdown へ書き出し（`data/exports/`）
- **復元手順**: bot を停止 → `data/otaku-assistant.db` をバックアップで差し替え → 起動
- 注意: バックアップは**同じサーバー内**に置かれます。マシン障害に備えるには
  `data/backups/` を rsync 等で外部へ退避する cron を別途組んでください

### スケジューラ（基盤）

リマインダー等の時間駆動機能は共通のスケジューラで動いています。

- ジョブは SQLite に永続化され、**再起動・デプロイを跨いで生存**します
- bot 停止中に期限が来たジョブ: 単発は再起動後すぐ実行、定期は1回だけ実行して次回へ
- プラグインを無効化すると、そのプラグインのジョブは `orphaned` として停止します（再試行なし）

### トラブルシュート

| 症状 | 確認すること |
|---|---|
| コマンドが出てこない | `npm run register-commands` を実行したか。config で enabled になっているか |
| リマインダーが届かない | 対象ユーザーが bot からの DM を許可しているか。ログの `Scheduled job failed` |
| 中継が止まった | バリアの deny-by-default。`/timeline-barrier list` と `test` で確認 |
| 検索がヒットしない | 3文字以上で検索したか。閲覧権限のないチャンネルは出ない仕様 |
